# Выбор SNI для Reality

Reality маскирует трафик под TLS к чужому сайту. Если цель выбрана неправильно,
подключение либо не устанавливается, либо выглядит подозрительно для DPI.
`google.com:443` из примеров — плохой выбор: он заблокирован во многих сетях,
отвечает нестабильно и слишком популярен как заглушка.

## Требования к цели

| Требование | Как проверить | Почему |
|---|---|---|
| TLS 1.3 | `openssl s_client -tls1_3 -connect <HOST>:443` | Reality работает только на 1.3 |
| HTTP/2 | `curl -sI --http2 https://<HOST>` → `HTTP/2` | h2 — обычный профиль для такого трафика |
| Валидный серт на это имя | `openssl s_client ... \| openssl x509 -noout -subject -issuer` | Иначе handshake выглядит фальшиво |
| Стабильный и быстрый | `for i in 1 2 3; do curl -so /dev/null -w '%{time_total}\n' https://<HOST>; done` | Медленная цель = медленный VPN |
| Не заблокирован в целевых сетях | проверить из страны пользователя | Иначе VPN «не работает» без причины |
| Не ваш собственный домен | — | Свой домен связывает сервер с вами |
| Без редиректов на другие хосты | `curl -sI https://<HOST>` | Redirect ломает иллюзию |

## Кандидаты

Массовые CDN и облака, которые почти всегда доступны и держат TLS 1.3 + h2:

```
www.microsoft.com
www.cloudflare.com
www.apple.com
dl.google.com
www.lovelive-anime.jp
gateway.icloud.com
```

Проверять кандидатов **с самого сервера** — важна его сеть, а не ваша.

## Проверка одной командой

```bash
SNI=www.microsoft.com
openssl s_client -tls1_3 -servername "$SNI" -connect "$SNI:443" </dev/null 2>/dev/null \
  | openssl x509 -noout -subject -dates
curl -sI --http2 "https://$SNI" | head -1
```

Оба ответа непустые и без ошибок — цель годится.

## Про сканер подсети

`RealiTLScanner` сканирует диапазон и показывает, какие хосты отвечают TLS.
Полезно, чтобы найти **локально доступные** цели, но:

- сканировать свою /24 бессмысленно — там соседи по хостингу, а не стабильные сайты;
- вывод сканера — кандидаты, а не готовый ответ: каждый надо проверить `openssl`;
- результат сканера должен попасть в `dest` и `serverNames`, иначе сканирование
  было театром (в v2.0 результат выбрасывался, а в конфиг шёл `google.com:443`).

Запуск (диапазон осмысленный, не свой):

```bash
/tmp/scanner --addr <CIDR> --port 443 --timeout 2 2>&1 | head -40
```

## Что попадает в конфиг

```json
"realitySettings": {
  "dest": "<SNI>:443",
  "serverNames": ["<SNI>"],
  "privateKey": "<PRIV>",
  "shortIds": ["<SID>"]
}
```

`dest` и `serverNames` — одно и то же имя, `spx` в ссылке — `/`.
Если хост за Cloudflare, `dest` иногда лучше указывать как IP:443 с тем же
`serverNames` — проверяется только сквозным тестом.

## Признак удачной маскировки

Снаружи порт выглядит как обычный HTTPS к выбранному сайту: `openssl s_client`
без Reality-параметров показывает сертификат этого сайта, `curl https://<IP>:<PORT>`
не отдаёт ничего осмысленного. Это нормально и ожидаемо; проверять работоспособность
надо клиентом, а не `curl` с сервера на себя.
