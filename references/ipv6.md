# IPv6: утечка мимо туннеля, проверка и два сценария

Коротко: IPv6 — это второй независимый путь в интернет. Если туннель несёт только
IPv4, а на машине/у клиента есть рабочий IPv6, часть трафика уходит напрямую и
exit IP перестаёт быть вашим. Поэтому решение всегда бинарное: либо IPv6 выключен
целиком, либо он завёрнут в туннель и закрыт файрволом. «Наполовину» — это утечка.

## Почему dual-stack даёт утечку

| Механизм | Что происходит |
|---|---|
| VPN ставит маршрут только `0.0.0.0/0` | Клиентская ОС продолжает видеть свой IPv6 default route; приложение с AAAA-адресом уходит мимо tun-интерфейса |
| DNS вне туннеля | Резолвер отдаёт AAAA, приложение соединяется по IPv6 напрямую — даже если IPv4-трафик полностью в туннеле |
| «Умные» клиенты и split tunnel | Исключения по приложениям/подсетям почти всегда IPv4-only; IPv6 в них не попадает и идёт напрямую |
| Сервер слушает только `0.0.0.0` | Клиент с AAAA на домене получает отказ/таймаут по v6; happy eyeballs уводит на v4 — это не утечка, но задержка и странные ошибки |
| ufw с `IPV6=no` | v6-трафик на сервере не фильтруется вообще: открытые v6-порты в обход правил |
| Свой v6 default на сервере | `freedom`-outbound резолвит домен в AAAA и выходит по v6: exit IP «прыгает» между семействами, геолокация и `--expect` ломаются |

Проверять надо с двух сторон: на сервере (что у него есть) и с клиента (куда
реально уходит трафик). Утечка видна так: `curl -6` с клиента возвращает домашний
адрес, а не адрес сервера.

## Как проверить (сервер, всё read-only)

```bash
ip -6 addr show                  # глобальные адреса, не только ::1 и fe80::
ip -6 route show default         # есть ли default via ... ; пусто = v6 наружу нет
ip -6 route get 2001:db8::1      # какой src и dev выберет ядро
sysctl net.ipv6.conf.all.disable_ipv6 net.ipv6.conf.default.disable_ipv6
curl -6 -s --max-time 8 https://ipv6.icanhazip.com; echo
curl -4 -s --max-time 8 https://ipv4.icanhazip.com; echo
ss -6 -tulpn                     # кто слушает на [::] и [::1]
grep -E '^IPV6=' /etc/default/ufw
ufw status verbose
```

| Видим | Значит |
|---|---|
| `inet6 2001:db8::10/64 scope global` + default route | полноценный dual-stack: v6 надо либо гасить, либо заворачивать в туннель |
| только `::1` и `fe80::` | глобального v6 нет, утечки с сервера нет; клиентская утечка всё равно возможна |
| `curl -6` → «Network is unreachable» | v6-выхода нет — это нормально для сценария A |
| `curl -6` вернул адрес, отличный от v4-адреса | у сервера два разных выхода; проверяйте, какой из них ожидается |
| `[::]:8443` в `ss`, а правило ufw только под v4 | порт открыт в v6 мимо ожиданий |
| `IPV6=no` в `/etc/default/ufw` | ufw не фильтрует v6 совсем |

То же самое печатает `scripts/server_audit.sh` в секции `IPv6 / ROUTES`
(адреса, default route, `disable_ipv6`, exit IPv6, AAAA домена, слушатели `[::]`,
статус `IPV6=` у ufw). Домен для AAAA задаётся аргументом
(`bash scripts/server_audit.sh vpn.example.com`) или переменной `AUDIT_DOMAIN`,
по умолчанию берётся `hostname -f`.

Клиентская проверка (выполнять на устройстве, где включён VPN):

```bash
curl -4 -s https://ipv4.icanhazip.com   # должен быть адрес сервера
curl -6 -s https://ipv6.icanhazip.com   # либо адрес сервера, либо ошибка сети
```

Если `curl -6` отдаёт домашний/мобильный адрес — трафик идёт мимо туннеля.

## Сценарий A: IPv6 не нужен — выключить

Подходит, когда клиенты ходят только по IPv4, AAAA у сервисных доменов нет и
панель не опубликована по v6.

1. Убедиться, что никто не слушает v6 и нет v6-only сервисов:

   ```bash
   ss -6 -tulpn | grep -v '\[::1\]'
   ```

   Если там xray с `listen: "::"` — сначала переведите inbound на `0.0.0.0`
   (см. сценарий B), иначе после выключения v6 он перестанет принимать.
2. Выключить в ядре и сохранить:

   ```bash
   cat > /etc/sysctl.d/99-disable-ipv6.conf <<'EOF'
   net.ipv6.conf.all.disable_ipv6 = 1
   net.ipv6.conf.default.disable_ipv6 = 1
   EOF
   sysctl --system
   ```

   `all` применяется к существующим интерфейсам (включая `lo`), `default` — к тем,
   что появятся позже (veth, tun, wg). Если локальным сервисам нужен `::1`
   (redis/postgres/некоторые панели слушают `[::1]`), добавьте
   `net.ipv6.conf.lo.disable_ipv6 = 0` — но тогда проверьте, что на `lo` нет
   ничего лишнего.
3. Проверить, что адреса и маршрут действительно исчезли:

   ```bash
   sysctl net.ipv6.conf.all.disable_ipv6          # 1
   ip -6 addr show                                # глобальных адресов нет
   ip -6 route show default                       # пусто
   curl -6 -sS --max-time 5 https://ipv6.icanhazip.com   # Network is unreachable
   grep -c . /proc/net/if_inet6                   # 0
   ```

   Отсутствие default-маршрута и есть гарантия: пакету физически некуда идти,
   поэтому «утечки» через v6 не будет.
4. Жёсткий вариант — выключить стек в загрузчике: `ipv6.disable=1` в
   `GRUB_CMDLINE_LINUX` + `update-grub` + reboot. После этого `/proc/sys/net/ipv6`
   отсутствует и включить v6 на ходу нельзя. Минусы: docker-сети с `--ipv6`
   перестанут работать, а `ipv6.disable` несовместим с частью container-runtime.
5. Если v6-адрес выдан провайдером по SLAAC, полезно также
   `net.ipv6.conf.<if>.accept_ra = 0` и `autoconf = 0`, чтобы адрес не вернулся
   при смене сетевых настроек.
6. Закрыть v6-правила на внешнем firewall/в панели хостера: если адрес остался
   маршрутизируемым, провайдерский фильтр — единственный барьер.
7. Проверка с клиента: `curl -6` должен падать, `curl -4` — возвращать адрес
   сервера. Сквозная проверка: `scripts/verify_vless.py --family 4 --expect-family 4`.

Предупредите пользователя: выключение v6 на ходу рвёт SSH-сессии, пришедшие по
v6, и ломает сервисы, слушающие `[::1]`.

## Сценарий B: IPv6 нужен — поднять v6-inbound

1. Убедиться, что к серверу есть глобальный v6 и default route:

   ```bash
   ip -6 addr show scope global
   ip -6 route show default
   ping -6 -c2 2001:db8::1        # или любой внешний v6-хост
   ```

   Если default route нет (бывает только on-link `/64`), добавить и сохранить:
   `ip -6 route add default via <GW6> dev <if>`. В ifupdown/netplan это
   `gateway6`/`routes`; после ребута проверить снова.
2. В 3x-ui добавить отдельный inbound:
   - protocol `vless`, security `reality`, свой порт (например 8444 — не тот, что
     у v4-inbound);
   - listen `::` (или конкретный v6-адрес сервера — ещё лучше: тогда сокет не
     конфликтует с v4-портом);
   - ключи Reality можно те же, что у v4-inbound, но SNI/`shortId` лучше другие,
     чтобы ссылки не путались.
3. Не вешать `::` на тот же порт, что `0.0.0.0`: при `net.ipv6.bindv6only=0`
   (значение по умолчанию) сокет `::` принимает и v4-mapped, поэтому получаете
   `EADDRINUSE` либо неожиданный захват v4-трафика. Проверка:
   `sysctl net.ipv6.bindv6only`.
4. Открыть порт в ufw (правило применяется к обоим семействам, если `IPV6=yes`):

   ```bash
   grep -E '^IPV6=' /etc/default/ufw
   ufw allow 8444/tcp
   ufw reload
   ufw status verbose | grep 8444
   ```

   Если `IPV6=no`: `sed -i 's/^IPV6=.*/IPV6=yes/' /etc/default/ufw && ufw reload`.
   Не забыть внешний firewall/security group — он фильтрует отдельно.
5. Проверить, что сокет слушает именно v6, и что порт доступен:

   ```bash
   ss -6 -tulpn | grep 8444                  # [::]:8444
   nc -6 -vz 2001:db8::10 8444               # succeeded
   ```

6. Ссылка для клиента: IPv6-литерал в URI — в квадратных скобках, иначе клиент
   не распарсит:

   ```
   vless://<UUID>@[2001:db8::10]:8444?type=tcp&security=reality&pbk=<PUBKEY>&fp=chrome&sni=<SNI>&sid=<SID>&flow=xtls-rprx-vision#v6
   ```

   В JSON-конфиге xray, наоборот, скобок нет: `"address": "2001:db8::10"`.
7. Проверка с сервера: `scripts/verify_vless.py --ip 2001:db8::10 --family 6
   --expect-family 6`. Успех = exit IP принадлежит IPv6 и равен ожидаемому.
   С клиента — `curl -6 -x socks5h://127.0.0.1:<local-socks> https://ipv6.icanhazip.com`.
8. Если нужен v6 и на исходящем трафике (`freedom`), проверьте, что сервер сам
   ходит в v6: `curl -6 https://ipv6.icanhazip.com` без прокси. Иначе v6-inbound
   будет принимать соединения, но наружу ничего не пустит.

Публиковать AAAA для сервисного домена не обязательно: клиенты с happy eyeballs
начнут предпочитать v6, и любая поломка v6-пути станет «VPN не работает».
Проще выдавать v6-ссылку явно.

## Грабли

**Docker и IPv6.** По умолчанию `docker0` имеет только link-local, контейнеры
наружу по v6 не ходят. Для v6-сети нужен `daemon.json`:

```json
{
  "ipv6": true,
  "fixed-cidr-v6": "2001:db8:1::/64",
  "ip6tables": true,
  "experimental": true
}
```

и `systemctl restart docker`. UFW такие сети не фильтрует: docker вставляет свои
правила в `DOCKER`/`nat` раньше ufw, и `-p 8443:8443` открывает порт в v4 и v6
мимо ваших `ufw allow`. Смотреть: `iptables -t nat -S DOCKER`,
`ip6tables -t nat -S DOCKER`. Контейнер с v6-default может утекать мимо туннеля,
если VPN поднят внутри контейнера, — гасите v6 внутри или маршрутизируйте его.

**xray `domainStrategy`.** У `freedom`/`vless` outbound по умолчанию `AsIs`:
домен уходит системному резолверу, и семейство exit IP зависит от A/AAAA и
happy eyeballs. Для детерминированного результата ставьте `UseIPv4` или
`UseIPv6` (это и делает `verify_vless.py --family 4|6`). Важно: стратегия влияет
только на резолв доменов — литеральный IPv6-адрес в запросе всё равно пойдёт по
v6. И routing-правила могут перебить outbound: если стратегия «не работает»,
смотрите `routing.rules` и `balancers`.

**Happy Eyeballs (RFC 8305).** Клиентские ОС опрашивают A и AAAA параллельно и
предпочитают v6 (RFC 6724). Если v6-путь «полуживой» — пакеты уходят, ответы нет,
— соединение всё равно установится по v4, но с задержкой; а если v6-путь живой и
не в туннеле, оно молча уйдёт мимо. Лечится только явным выбором: v6 выключен
или полностью завёрнут. Тесты `curl -4` и `curl -6` по отдельности, не «просто
curl».

**MTU.** Минимальный MTU для IPv6 — 1280, а PPPoE (1492), WireGuard (1420) и
разные туннели его уменьшают. Заголовки v6 на 20 байт длиннее, плюс PMTUD в
туннеле часто сломан → TCP-хендшейк с большим сертификатом зависает, а ping
проходит: классическое «v6 медленный/не работает, v4 нормально». Ставьте MTU
туннеля/интерфейса (1420/1380) и клампьте MSS:

```bash
iptables -t mangle -A FORWARD -p tcp --syn -j TCPMSS --clamp-mss-to-pmtu
ip6tables -t mangle -A FORWARD -p tcp --syn -j TCPMSS --clamp-mss-to-pmtu
```

**Формат адреса.** Три разных синтаксиса, путаница — самая частая ошибка:
URI/curl — `[2001:db8::10]:8443`; xray JSON — `"2001:db8::10"` без скобок;
link-local требует зоны — `fe80::1%ens3`, и в JSON её тоже надо передавать.
`verify_vless.py` снимает квадратные скобки с `--ip` сам, но в vless:// они
обязательны.

**`::` и файрвол.** Правило `ufw allow 8443/tcp` покрывает оба семейства только
при `IPV6=yes`; правило, добавленное при `IPV6=no`, v6 не откроет. А `::/0`
в `ufw route`/`before.rules` может случайно открыть больше, чем ожидалось.

**Смена `disable_ipv6` на ходу.** Убирает адреса со всех интерфейсов сразу,
включая `lo`; процессы, слушающие `[::1]`, начинают падать в `bind: cannot
assign requested address`. Смотрите `ss -6 -tulpn | grep '\[::1\]'` до, а не после.

## Что докладывать

Разделяйте: что проверено на сервере (адреса, маршрут, sysctl, слушатели, ufw),
что проверено с клиента (`curl -4`/`curl -6`), и что осталось на стороне
пользователя (клиентский конфиг, отключение v6 на телефоне, внешний firewall).
«IPv6 выключен» подтверждается пустым `ip -6 route show default` и падающим
`curl -6`, а не только значением sysctl.
